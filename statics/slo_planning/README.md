# statics/slo_planning/

## `c2_plans_old.csv`: the plans of the first deployment (run on the testbed)

One row per scenario (S-V-1 to S-L-5) of Evaluation C.2: the chosen composition (`composition` is the short label V1 to
L5, `experiment` the chain `b1u-<application>-<i>`), its total workers, the predicted p95 bound (`predicted_p95_ms`) and
the knobs to deploy (`knobs`: `shared.data_quality`, `<node>.parallelism`, `<node>.cores` = parallelism + 0.5,
`<node>.model_size`). The figures `figures/tsc/experimental-results/c2_slo_plans_<application>.{jpg,pdf}` show the same
plans. Their testbed runs are in `statics/results_milos_v2/c2/`; C.2d of `notebooks/tsc/2f_optimization.ipynb` compares them.

**This file and these figures are not regenerated by the notebook.** The notebook rewrites the figures only if
`WRITE_DEPLOYED_FILES` in its setup cell is `True`.

## `c2_plans_new.csv`: the plans of the current models (to deploy)

Same columns as `c2_plans_old.csv` plus `best_effort`, written by every run of the notebook (cell "Configurations to
deploy"): the plans that the grid search infers with the current load-aware models of B.1. `feasible` means that the
configuration meets every SLO. If no configuration does (S-A-2 at the time of writing), `feasible` is False,
`best_effort` is True and the row holds the configuration with the smallest predicted bound among those that meet the
other constraints.

## Why a rerun of the notebook gives other plans

The plans of `c2_plans_old.csv` were computed with the load-aware models of B.1 as they were trained until 2026-11-06:

| | `c2_plans_old.csv` | Notebook on `main` now |
|---|---|---|
| Training runs of a service | its benchmark (one worker) plus its runs in the other chains of the campaign, without the chain being planned (`extended_pool`, `chain_family`) | the benchmarks with one to four workers only (`worker_benchmark_pool`); no chain runs |
| Handover between services | a constant of about 1.5 ms per handover, measured on the other chains, added to the end-to-end bound | none |

The commit `4be6d38` ("train on per-worker benchmarks only, drop hop and handover constants, ...") made that change for
all of B and C. The solver (SLSQP on the continuous relaxation, the weights on typical values, the scenarios) is the
same in both; only the node bounds that it optimizes over differ. Rerunning the notebook now gives the same
composition for most scenarios, but other workers, data qualities and bounds for many of them, and no plan for S-A-2
(voice assistant, p95 ≤ 50 ms).

## Reproducing the deployed plans

The code that produced them is the commit `c84c2df` (2026-11-06), kept as the git tag `archive/c2-slo-planning`
(the branch `c2-slo-planning` was deleted). Running `2f_optimization.ipynb` on that commit fits the models under the old training pool
(`models_<chain>_<key>.joblib`, about a minute per composition; the old cache files are no longer in this folder) and
writes this file and the figures. Note that the tag is
based on `614d786`, before the switch described above; check it out in a separate worktree
(`git worktree add <path> archive/c2-slo-planning`) rather than in this one.
